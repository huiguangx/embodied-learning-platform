# EIP 训练平台：项目介绍、流程理解与面试问答

## 使用原则

本材料基于已登录环境的页面采集，不替代源代码、架构图或线上运行数据。面试时必须区分：

- **已上线/已验证**：集群看板、开发机、自定义训练任务、镜像中心、对象存储等页面实际可见的能力。
- **设计中/规划中**：实验管理、模型仓库、在线服务、弹性资源任务等当前仍显示“功能正在开发中”的能力。

不要将后者表述为已经完成的生产能力。

## 1. 一分钟项目介绍

EIP 是面向具身智能和 AI 算法团队的内部训练与算力运营平台。它解决的核心问题是：多集群 GPU 资源分散、训练环境和数据来源不统一、任务结果不可追溯，以及模型难以从训练流转到交付。

平台当前已经提供了 Cloud、IDC 等集群的 GPU/CPU/内存态势看板，开发机管理、自定义训练任务管理、镜像中心和对象存储浏览。算法工程师可以选择资源和运行环境，提交或复用训练任务，并查看任务状态与资源规格；平台管理员可以通过集群和资源侧入口管理容量、队列和权限。总体目标是把“资产准备、资源调度、训练执行、实验沉淀、模型管理、在线服务”连接为一条可追溯的研发闭环。

## 2. 三分钟项目介绍

### 背景与痛点

具身智能训练通常有大规模数据、异构 GPU、复杂容器环境和长时间任务。团队若直接使用脚本加云控制台，会出现四类问题：

1. 算力不可见：不知道哪个集群空闲、节点是什么型号、任务为何长期排队。
2. 环境不可复现：镜像、代码、数据、参数和资源规格分散在不同地方。
3. 资源缺少治理：多人抢占 GPU，没有项目配额、队列和预约边界。
4. 产物难交付：训练模型、实验指标与部署服务之间缺少稳定关联。

### 当前已实现的产品能力

- **集群看板**：可按 Cloud、IDC 集群查看 GPU 在线数、利用率、显存使用、CPU/内存、任务统计以及节点负载。
- **开发机**：用户按归属、状态、集群查询个人开发机，并查看计算规格、云盘、队列、描述和运行时长。
- **自定义训练**：任务列表支持按归属、名称/ID、状态和集群筛选；每条任务展示框架、队列、优先级、实例/GPU 数、资源规格、生命周期时间和创建人，并有复制、编辑、删除入口。
- **资产入口**：镜像中心支持按仓库实例、命名空间和镜像名称检索；对象存储支持选择 Bucket 并浏览文件目录。

### 设计方向

平台一期目标不是自研 Kubernetes、镜像仓库或对象存储，而是在这些基础能力之上建立统一控制面。训练任务固定引用镜像 digest、代码版本、数据集版本、资源组和队列；任务完成后自动沉淀实验运行和产物，选定产物注册模型版本，再发布为在线服务。这样可以在任意模型或服务上追溯到训练输入和运行条件。

### 我在项目中的典型职责表达

请按自身实际经历替换，不要虚构：

> 我负责训练平台中【模块名称】的【产品/前端/后端/平台工程】工作。重点解决了【具体问题】。我与算法、运维和数据团队确定了【接口/数据模型/权限边界】；通过【技术方案】实现【结果】；最终用【指标或验收案例】验证效果。对于仍在规划的实验、模型和在线服务模块，我参与了需求和技术设计，但不会表述为已上线。

## 3. 平台流程理解

### 已验证的当前流程

```text
首页看集群健康度与负载
  -> 资产中心查找镜像和对象存储数据
  -> 选择队列/资源（资源菜单已有入口）
  -> w
  理任务
  -> 运行状态和资源规格在任务列表中跟踪
  -> 需要交互调试时进入开发机
```

### 目标闭环流程

```text
数据集版本 + 代码版本 + 镜像 digest
  -> 资源组/队列/预约预检
  -> 提交训练任务
  -> 调度并运行，采集日志、指标、检查点和产物
  -> 自动生成实验运行，比较并标记最佳结果
  -> 注册模型版本，审批发布
  -> 创建在线服务并监控状态、延迟和错误率
```

### 关键业务对象

| 对象 | 含义 | 为什么重要 |
| --- | --- | --- |
| 项目空间 | 成员、资产、资源和成本的隔离边界 | 防止跨团队误用资源和数据。 |
| 资源组 | 项目可使用的集群范围和配额 | 把资源治理从“人找机器”变成规则。 |
| 队列 | 任务排队与优先级策略 | 在资源紧张时保证公平和业务优先级。 |
| 训练任务 | 一次可调度的训练执行单元 | 固定记录环境、输入、资源和状态。 |
| 实验运行 | 一次训练的参数、指标、日志和产物记录 | 支持比较与结果选择。 |
| 模型版本 | 可复用、可审批、可追溯的模型产物 | 连接训练和服务。 |
| 在线服务 | 对外提供推理能力的部署单元 | 连接模型研发和业务交付。 |

## 4. 30 秒亮点回答

### 亮点一：可追溯性，而不仅是提交任务

平台的关键不是把 Job 发到集群，而是让每个训练任务固定引用镜像 digest、代码版本、数据版本、参数、资源规格和输出路径。模型上线后可以反查到完整训练上下文，从而支持复现、审计和问题定位。

### 亮点二：多集群资源治理

页面已体现 Cloud、IDC 和其他集群的统一入口。合理的设计是将不同集群能力抽象成统一资源规格，在资源组、队列、配额、预约层完成治理，再由适配器映射到底层调度系统。这样上层产品不与单一集群实现耦合。

### 亮点三：开发与训练衔接

开发机用于交互式调试，训练任务用于可复现、可调度的批量执行。高效流程是用户在开发机验证环境后，将镜像、代码提交、数据版本和参数固化为任务模板，再提交到队列中运行。

## 5. 高频面试问答

### Q1：这个项目的业务价值是什么？

**答**：它把算法研发需要的算力、环境、数据、训练和交付能力统一起来。对算法同学，它减少了找资源、配环境和人工记录实验的时间；对运维和管理员，它提供了多集群容量可视化、配额和队列治理；对组织，它让训练产物可追溯并可沉淀成可复用模型与服务。

### Q2：为什么不直接让用户使用 Kubernetes 或云厂商控制台？

**答**：底层控制台只解决资源编排，不理解项目权限、数据版本、算法任务模板、实验指标和模型发布。EIP 在上面增加领域抽象与治理：用户操作的是训练任务、资源组和模型，而不是裸 Pod；同时平台保留对底层调度器的适配能力，避免重复造轮子。

### Q3：自定义训练任务需要保存哪些信息？

**答**：至少包含项目、创建人、任务模板版本、镜像 digest、代码版本、数据集版本、命令和超参数、队列与资源组、CPU/内存/GPU 请求与限制、分布式规格、输入输出路径、状态、日志/指标/产物 URI，以及创建、开始、结束时间。镜像必须记录 digest 而不是仅记录 tag，避免 tag 被覆盖后无法复现。

### Q4：怎样设计训练任务状态机？

**答**：建议 `草稿 -> 待校验 -> 排队 -> 分配中 -> 运行中 -> 成功/失败/已取消/已停止/超时`。状态转换由编排服务控制，用户只能发起停止或取消请求，不能直接把运行中任务改成完成。外部回调可能重复或乱序，因此要带资源版本或事件序号，并拒绝状态回退。

### Q5：如何保证一次训练可复现？

**答**：将所有可变输入版本化并固定引用：镜像用 digest、代码用 commit SHA、数据用数据集版本或清单 checksum、依赖和参数写入任务快照、资源规格和启动命令全部入库。输出记录对象存储 URI、校验和和实验 ID。任务复制时复制配置快照而不是修改历史记录。

### Q6：多集群环境下怎么调度？

**答**：上层定义统一资源请求，如 GPU 型号/数量、CPU、内存、节点约束、网络和存储能力。预检阶段根据资源组权限和集群能力筛选候选集群，再由队列策略选择落点。底层差异由适配器处理，例如不同集群的节点标签、存储类和调度 API。失败时返回“配额不足、无匹配节点、预约保留”等可行动原因。

### Q7：队列和资源组有什么区别？

**答**：资源组定义“谁能使用哪些资源以及上限是多少”，如项目成员、集群范围、GPU 配额和并发数；队列定义“这些请求如何排队和调度”，如优先级、权重、最大运行时长和抢占策略。将二者分开，可以同时满足权限隔离和公平调度。

### Q8：遇到 GPU 配额不足如何处理？

**答**：提交前做预检，明确返回资源组剩余配额、队列容量和可选替代项。用户可降低规格、换队列、等待、申请预约或请求管理员审批。不能在提交后静默失败，也不能让超配任务绕过治理直接落到集群。

### Q9：开发机和训练任务为什么要分开？

**答**：开发机强调交互性，适合调试、探索和 Notebook/IDE 使用；训练任务强调可复现性和吞吐，适合批量、分布式、可排队执行。若混用，交互式实例容易长期占用 GPU，训练任务也难以复现。两者可以共享镜像、数据和资源组，但生命周期策略不同。

### Q10：如何设计实验管理？

**答**：训练启动时自动创建实验运行，采集参数、指标、日志、资源使用、检查点和产物。实验页面支持按标签、任务、数据版本和时间筛选，支持多运行指标比较。实验运行本身不能被随意改写，用户可增加标签和备注；选定产物再注册为模型版本。

### Q11：模型仓库为什么不能只是对象存储目录？

**答**：对象存储解决“文件在哪里”，模型仓库解决“这个文件是什么、如何使用、能否发布以及从哪里来”。模型版本需要格式、推理签名、依赖镜像、指标、训练来源、审批和生命周期。这样在线服务可以消费明确的模型版本，而不是人工填一个路径。

### Q12：在线服务如何做版本发布和回滚？

**答**：一期可使用滚动更新：创建新版本实例，健康检查通过后逐步替换旧实例；保留上一个稳定版本及其配置，一旦健康检查或错误率异常可以回滚。后续可增加按流量比例的灰度与 A/B。模型版本、推理镜像和服务配置都应不可变快照化。

### Q13：如何做权限和数据隔离？

**答**：以组织、项目、资源组三层建立 RBAC；所有 API 都在项目上下文中鉴权。对象存储、镜像和模型不能把永久凭据暴露给前端，而应由后端校验后签发短期凭据或代理访问。训练运行环境也使用最小权限身份，审计记录所有写操作。

### Q14：如何避免训练任务被重复提交？

**答**：创建接口支持 `Idempotency-Key`，服务端按项目和键保存首次结果；编排层也以任务 ID 作为幂等提交键。这样网络重试不会创建多个实际 Job。事件消费同样去重，并要求状态机单向流转。

### Q15：训练平台如何观测和排障？

**答**：任务、实验和服务都要带统一标签：项目、任务 ID、实验 ID、模型版本、服务 ID。日志、指标和事件通过这些标签关联。用户界面显示状态、失败分类、日志入口、资源利用率和关键指标；平台运维增加调度延迟、镜像拉取、节点异常和队列等待等系统指标。

### Q16：如果调度器不可用，平台如何保证一致性？

**答**：创建训练先持久化任务并进入“待校验/分配中”，异步调用调度适配器。适配器超时不直接标失败，而是按幂等键重试并定时对账实际集群状态。只有确认底层不存在对应工作负载且重试耗尽后才标为失败。这样可以处理“提交成功但响应超时”的典型分布式不确定性。

### Q17：项目中最容易被忽略的安全问题是什么？

**答**：一是把对象存储或镜像仓库的长期凭据放到任务参数/环境变量/前端；二是跨项目引用资产；三是训练镜像以高权限运行；四是日志泄漏 token。需要用短期凭据、项目级授权、最小权限运行身份、镜像准入策略和日志脱敏处理。

### Q18：如何拆分一期和后续版本？

**答**：一期的终点是最小训练闭环：项目与权限、资产版本引用、资源组/队列、训练任务、实验记录、模型注册、最小在线发布。弹性资源、服务自动扩缩、灰度/A/B、智能选型、深度仿真联动属于二期以后。这样先验证闭环价值，避免同时建设所有平台能力。

### Q19：你如何衡量平台是否成功？

**答**：业务指标包括训练提交时长、任务成功率、从训练到模型发布的时长、复现实验的成功率；资源指标包括 GPU 利用率、排队时间、预约兑现率和闲置时长；质量指标包括状态同步错误率、资产权限拒绝率和服务可用性。指标必须按项目和集群分层观察。

### Q20：当前页面中哪些能力是已上线，哪些不能夸大？

**答**：已验证的是集群看板、开发机、自定义训练、镜像中心和对象存储浏览。弹性资源任务、实验管理、在线服务、模型仓库在采集时显示“功能正在开发中”。资源组、队列和预约有菜单入口，但具体实现需要结合代码和接口进一步确认。因此我会将后者表述为平台规划或设计方向，而不是现成能力。

## 6. 可能的追问与回答框架

| 追问 | 回答框架 |
| --- | --- |
| 任务为何失败？ | 区分用户代码、镜像拉取、权限、资源不足和平台异常；给出可操作恢复路径。 |
| 为什么需要预约？ | 为大规模或关键训练预留确定性容量，避免只靠排队导致项目风险。 |
| 怎么支持成本控制？ | 资源组绑定成本中心，按任务 GPU 时间、规格和集群价格归集；预警而非只做事后报表。 |
| 如何迁移已有脚本任务？ | 提供 CLI/API 与任务模板导入，先固化镜像、命令、参数与数据版本，再逐步纳入队列治理。 |
| 如何避免平台成为瓶颈？ | 控制面与数据面分离；大文件直传对象存储；任务状态异步事件化；读模型和指标查询独立扩展。 |

## 7. 面试收尾话术

> 这个项目让我理解到 AI 平台的难点不只是训练任务的提交，而是将资产版本、资源治理、异步任务状态和模型交付连接成可追溯闭环。当前平台已落地训练和资产基础能力，下一阶段最有价值的是补齐实验、模型和在线服务，并以项目与资源组为边界建立可量化的资源效率和成本治理。
